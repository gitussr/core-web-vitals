WordPress Core Web Vitals guide

How to score 100 on PageSpeed Insights with WordPress

https://gitussr.github.io/core-web-vitals/

A complete Core Web Vitals and Lighthouse guide: how PageSpeed Insights awards its points in Performance, Accessibility, Best Practices and SEO, the hidden criteria nobody tells you about, and the decisions to make from the first line of HTML — long before the site becomes a WordPress theme.

Performance: 100
Accessibility: 100
Best Practices: 100
SEO: 100

What “100” really means

PageSpeed Insights (PSI) shows two completely different reports on one page. Knowing which is which is the first step.

Field data — “Discover what your real users are experiencing”

Comes from the Chrome User Experience Report (CrUX): real Chrome visitors over the last 28 days, judged at the 75th percentile. This is the Core Web Vitals assessment. It is Passed / Failed — there is no 100 here. Google Search uses this data as a ranking signal.

Lab data — “Diagnose performance issues”

A single Lighthouse run on Google’s servers with a simulated mid-range phone on a slow 4G connection. This produces the four 0–100 scores: Performance, Accessibility, Best Practices, SEO. This is where the “100” lives.

The goal is both: four 100s in the lab and a green Core Web Vitals assessment from real users. A lab 100 on a page that real users experience as slow (because of a cookie banner, a logged-in state, or slow servers at peak time) is a vanity score. Build for the field; use the lab to diagnose.

The four categories at a glance

Performance

Five measured timing metrics, each converted to a 0–1 score on a curve, then weighted. Opportunities and diagnostics do not count directly.

Weighted metrics

Accessibility

Automated axe-core rules. Each rule passes or fails for the whole page; heavier-impact rules carry more weight.

Weighted pass/fail

Best Practices

Security, modern APIs, console hygiene, image correctness and user-hostile behaviour checks.

Equal pass/fail

SEO

Technical crawlability and basic on-page metadata. It does not judge content quality or rankings.

Weighted pass/fail

How the Performance score is calculated

This is the hardest 100, and it is pure arithmetic. Once you understand the formula, you know exactly where your points are going.

Step 1 — Five metrics, five weights

  • First Contentful Paint10%
  • Speed Index10%
  • Largest Contentful Paint25%
  • Total Blocking Time30%
  • Cumulative Layout Shift25%

TBT, LCP and CLS make up 80% of the score. TBT is the single biggest lever — and it is almost entirely about JavaScript. INP (the field responsiveness metric) is not measured in a page-load test; TBT is its lab proxy.

Step 2 — Each metric becomes a score on a log-normal curve

Lighthouse doesn’t use pass/fail lines. Every metric is mapped onto a curve built from real-world HTTP Archive data with two control points: the value that earns a 0.90 score (top ~8% of sites) and the value that earns 0.50 (the median). The curve flattens near 1.0, so the last few points cost the most effort.

Performance = round( 100 × ( 0.10·FCP + 0.10·SI + 0.25·LCP + 0.30·TBT + 0.25·CLS ) )

//   0.30 × 0.03 = 0.009 lost  →  99

The test conditions you’re being graded under

Device

Emulated mid-range Android phone (Moto G Power class), 412 px wide viewport, with the CPU slowed down 4×.

Network

Simulated “slow 4G”: ~150 ms round-trip time and ~1.6 Mbps download. Every extra request in the critical path costs at least one RTT.

State

Cold load: empty cache, no cookies, no service worker, logged-out. Your page cache and CDN edge matter; browser caching does not.

Location

PSI runs from a Google data centre near the requester. A server far from that region inflates TTFB.

The audits under the score don’t add points. “Render-blocking requests”, “Improve image delivery”, “Reduce unused JavaScript” and the other insights are hints for moving the five metrics. You can have warnings there and still score 100, and you can fix every one and still score 92 if your server is slow.

Core Web Vitals — the field assessment

The pass/fail test real users give you. Each metric is judged at the 75th percentile of page views over 28 days, separately for mobile and desktop.

MetricMeasuresGoodNeeds improvementPoor
LCPLoading — when the largest image or text block renders≤ 2.5 s2.5 – 4.0 s> 4.0 s
INPResponsiveness — slowest interactions (click, tap, key) across the whole visit≤ 200 ms200 – 500 ms> 500 ms
CLSVisual stability — largest burst of unexpected layout shifts≤ 0.10.1 – 0.25> 0.25

Where is First Input Delay (FID)? FID was retired. INP replaced it as the responsiveness Core Web Vital on 12 March 2024, and FID was then removed from PageSpeed Insights, CrUX and Search Console (September 2024). If a tool or tutorial still reports FID, it is out of date.

Why it was replaced: FID measured only the delay before the browser began handling the first interaction (good was ≤ 100 ms). INP measures the full time from input to the next painted frame (input delay + processing time + presentation delay) for every click, tap and key press during the visit, and reports roughly the worst one. Nearly every site passed FID; many fail INP.

What carries over: FID was never part of the Lighthouse score either — Total Blocking Time (TBT) was, and still is, the lab proxy. Long main-thread tasks hurt TBT, used to hurt FID, and now hurt INP.

LCP is four sub-parts — fix the biggest one

Every LCP can be split into the four phases below. DevTools’ Performance panel and the Lighthouse “LCP breakdown” insight show them for your page.

1. Time to First Byte

Server and network time until the HTML starts arriving. Fix with full-page caching, a CDN and a fast PHP stack. Target ≤ 200 ms (cached).

~40%

2. Resource load delay

Gap between TTFB and the browser starting to download the LCP image. Fix by putting the image in the HTML with fetchpriority="high" — never in CSS backgrounds, sliders or JavaScript.

< 10%

3. Resource load duration

Download time of the LCP image itself. Fix with AVIF/WebP, correct dimensions via srcset, and a CDN.

~40%

4. Element render delay

Image is downloaded but not yet painted — blocked by CSS, fonts or JS, or hidden by an animation/slider. Fix by inlining critical CSS and never fading the hero in.

< 10%

Percentages are the ideal share of total LCP time recommended by the Chrome team.

INP is won during development, not launch

  • Keep every event handler under ~50 ms. Do the visual update first, then defer heavy work with await scheduler.yield() (with a setTimeout fallback).
  • Avoid giant DOMs (mega-menus with 2,000 nodes, page-builder nesting): style recalculation after a click scales with DOM size.
  • Third-party scripts (chat, A/B testing, tag managers) are the most common INP killers on WordPress sites.

How the Accessibility score is calculated

Lighthouse runs the axe-core engine. The score is a weighted average of the rules that apply to your page.

All-or-nothing

Each rule is binary for the whole page. One unlabeled icon button out of 50 fails the entire “Buttons have an accessible name” audit.

Weighted

Weights follow axe’s impact rating. Critical rules (names for buttons, links, images and form fields; valid ARIA) cost the most points; minor ones only a few.

N/A is free

Rules that don’t apply (no tables, no video) are excluded. Manual checks listed under “Additional items to manually check” are never scored.

Audits that most often break a WordPress site

Names & labelsCritical
  • Every <img> has meaningful alt, or alt="" if decorative. Set it in the Media Library; theme templates must output it.
  • Icon-only buttons and links (hamburger, search, social icons, slider arrows, cart) need visible text, aria-label or .sr-only text.
  • Every input has a <label for>. Placeholder text is not a label — check your search form and newsletter plugin.
  • <iframe> (maps, YouTube) needs a title.
  • Select menus, toggles and custom controls expose a name and role.
Colour contrastSerious
  • 4.5 : 1 for body text, 3 : 1 for large text (≥ 24 px, or ≥ 18.66 px bold).
  • Common failures: light-grey footer text, placeholder text, white text on brand orange/yellow buttons, text over hero images (add a solid overlay), disabled-looking “muted” captions.
  • Define accessible colours once in design tokens / theme.json so editors can’t pick failing pairs.
Document structureSerious
  • <html lang="…"> present and valid (WordPress’s language_attributes() does this).
  • A non-empty <title>.
  • Headings in sequential order — no jumping from h2 to h4 because the editor “liked the size”. Style with classes, not heading levels.
  • Lists contain only <li>; definition lists only <dt>/<dd>.
  • No duplicate id attributes referenced by ARIA or labels (frequent when a widget is repeated).
  • A skip link and one <main> landmark.
ARIA correctnessCritical
  • Only valid roles and attributes, and required children/parents (a role="tablist" must contain role="tab").
  • Never put aria-hidden="true" on an element that contains focusable links or buttons (off-canvas menus left in the DOM are the classic case — use inert or hidden).
  • No ARIA is better than wrong ARIA. Prefer native <button>, <details>, <dialog>.
InteractionSerious
  • Touch targets at least 24 × 24 CSS px, or spaced so a 24 px circle doesn’t overlap a neighbour (aim for 44 × 44 like Apple’s HIG).
  • Never disable zoom: no user-scalable=no or maximum-scale=1 in the viewport tag.
  • Links must be distinguishable from surrounding text without colour alone (underline or 3 : 1 contrast plus a non-colour hover/focus cue).
  • No positive tabindex values.

100 is the floor, not the ceiling. Automated checks catch roughly a third of real accessibility problems. Still test keyboard-only navigation, visible focus, screen reader announcements (VoiceOver: ⌘ F5), and 200% zoom.

The “Trust and Safety” group (effective CSP against XSS, strong HSTS, COOP origin isolation, clickjacking protection with frame-ancestors / X-Frame-Options) and “valid source maps” are shown for information. They don’t move the score today, but they protect the site, and Lighthouse has historically promoted informative audits into scored ones.

How the SEO score is calculated

Technical hygiene only. A 100 here means search engines can crawl and understand the page — not that it will rank.

Page isn’t blocked from indexing

No noindex in meta robots or the X-Robots-Tag header. This audit is weighted heavily — failing it alone drops the score dramatically.

Heaviest

Document has a <title> and a meta description

Unique per page. WordPress outputs the title via add_theme_support('title-tag'); description via your SEO plugin or theme.

Successful HTTP status code

The URL tested must return 200, not a 4xx/5xx. Redirect chains cost performance too.

Links have descriptive text

“Read more”, “Click here”, “Learn more”, “here” fail. Use “Read the case study: Acme redesign” or add visually-hidden context.

Links are crawlable

Every <a> needs a real href. href="#", href="javascript:void(0)" or JS-only click handlers fail. Use <button> for actions.

Images have alt attributes

Shared with accessibility — fix once, pass twice.

robots.txt is valid

If present, must parse. A malformed file from an old plugin fails this.

Valid hreflang and rel=canonical

Canonical must be absolute, unique and point to an indexable URL; hreflang codes must be valid. Conflicts between theme and SEO plugin output two canonicals — that fails.

Structured data validity is listed as a manual check: use Google’s Rich Results Test, but it doesn’t affect the score.

The hidden criteria

The things that quietly cost points on a site that “did everything right”.

  1. The default report is mobile, and mobile is about 4× harder

    A page that scores 100 on desktop often scores 75–85 on mobile. Design and test mobile-first from day one, on the throttled profile.

    Performance

  2. Your LCP element may not be what you think

    On mobile the LCP is often a heading paragraph, a cookie-consent banner or a lazy-loaded image — not your hero. Check the “LCP element” in the report. A cookie banner injected by JS late becomes LCP and also causes CLS.

    Performance

  3. The LCP image must be discoverable in the raw HTML

    Lighthouse’s “LCP request discovery” insight checks that the image is in the initial HTML, is not loading="lazy", and has fetchpriority="high". CSS background heroes, sliders and JS-rendered images all fail it.

    Performance

  4. Anything that animates in costs LCP and Speed Index

    Fade-in / slide-up on scroll libraries (AOS, page-builder “entrance animations”) delay paint of above-the-fold content. Never animate the hero or the first heading in.

    Performance

  5. Web fonts shift layout

    When the fallback font has different metrics, text reflows on swap and adds CLS. Use size-adjust/ascent-override fallbacks, or font-display: optional, and preload only the one or two critical files.

    Performance

  6. Late-inserted content above existing content

    Announcement bars, ad slots, “related posts”, consent banners pushed in at the top. Reserve space with min-height, or overlay them with position: fixed.

    CLS

  7. Scores vary between runs — design for a margin

    PSI results move ±3–5 points because of server load, network and CPU noise. Build to the “Aim for” values so that a bad run still rounds to 100. Judge by the median of five runs.

    All

  8. One console error costs Best Practices points

    Including a 404 favicon, a missing source map request, a console.error from a third-party widget, or a deprecated API used by a plugin.

    Best Practices

  9. Embeds set third-party cookies

    A single YouTube, Vimeo, Facebook or Instagram embed sets third-party cookies on load and fails Best Practices. Use a click-to-load facade.

    Best Practices

  10. Blurry or stretched images fail audits

    “Appropriate resolution” checks that the served image is large enough for the device pixel ratio; “correct aspect ratio” checks rendered vs natural shape. Logos are the usual culprit — use SVG.

    Best Practices

  11. “Discourage search engines” left on

    WordPress’s Settings → Reading checkbox adds noindex. Perfect on staging, catastrophic if it survives launch — and staging environments often add an X-Robots-Tag header too.

    SEO

  12. “Read more” links

    WordPress’s default excerpt link, card “Learn more” buttons and “View all” fail the descriptive link-text audit. Add context with visually-hidden text.

    SEO

  13. Hidden menus that remain focusable

    An off-canvas menu hidden with aria-hidden or transform but still tabbable fails ARIA audits. Use hidden, inert or visibility: hidden when closed.

    Accessibility

  14. What you test is not what users get

    Lighthouse tests logged out, with an empty cache, usually without consent. Test the logged-in admin bar view separately, and test with consent granted, because that’s when all the tags load.

    All

  15. Main-thread work from hydration and tag managers

    A single 300 ms task counts 250 ms toward TBT (anything above 50 ms per task is “blocking”). One analytics bundle can cost 5–10 points on mobile.

    TBT

  16. bfcache and unload handlers

    An unload listener (often from old analytics or chat scripts) disables the back/forward cache, so back-button navigations reload fully — bad for field LCP/INP and flagged by Lighthouse.

    Field

  17. One very long page fails mobile TBT on its own

    A 4,000-element document with no third parties and 3 KB of JS still scored 83 on mobile: laying out that much text is one long main-thread task, and on the 4× slowed CPU it becomes 300–600 ms of Total Blocking Time. Split long content into topic pages (better for SEO too) or keep each page’s DOM well under 1,500 elements.

    TBT

Design decisions that make 100 easy

  • Static hero: one image or pure typography
  • System font stack, or one variable font
  • Icons as inline SVG sprite
  • Click-to-load maps and video
  • Fixed-height header and reserved ad/banner slots
  • Contrast-checked palette defined as tokens

Design decisions that make 100 nearly impossible

  • Autoplay video or carousel above the fold
  • Hero fading/sliding in
  • 4+ font families or weights from Google Fonts
  • Icon fonts (Font Awesome full kit)
  • Live chat, pop-ups and social feeds on load
  • Heavy page builder with nested sections

Phase 1 — HTML foundations

Write the static HTML as if it were the final theme output. Everything here maps 1:1 onto WordPress template parts later.

The <head> order matters

Browsers process the head top to bottom. Charset first, then anything that unlocks the LCP, then styles, then deferred scripts.

Head template header.html

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">                                   <!-- 1. first, always -->
  <meta name="viewport" content="width=device-width, initial-scale=1">  <!-- never block zoom -->
  <title>Primary keyword – Brand</title>
  <meta name="description" content="150–160 characters that earn the click.">
  <link rel="canonical" href="https://example.com/page/">

  <!-- 2. Unlock LCP early: hero image + the one critical font -->
  <link rel="preload" as="image" fetchpriority="high"
        href="/img/hero-800.avif"
        imagesrcset="/img/hero-480.avif 480w, /img/hero-800.avif 800w, /img/hero-1200.avif 1200w"
        imagesizes="100vw" type="image/avif">
  <link rel="preload" as="font" type="font/woff2" href="/fonts/inter-var-latin.woff2" crossorigin>

  <!-- 3. Critical CSS inline (above-the-fold only, ≤ 14 KB) -->
  <style>/* reset, tokens, header, hero, first section */</style>
  <link rel="stylesheet" href="/css/main.css?v=1.0.3">

  <!-- 4. Scripts never block parsing -->
  <script src="/js/main.js?v=1.0.3" defer></script>

  <link rel="icon" href="/favicon.ico" sizes="32x32">         <!-- must exist: a 404 = console error -->
  <link rel="icon" href="/icon.svg" type="image/svg+xml">
  <link rel="apple-touch-icon" href="/apple-touch-icon.png">
</head>

The LCP hero, done right

<img src="/img/hero-800.avif"
     srcset="/img/hero-480.avif 480w, /img/hero-800.avif 800w, /img/hero-1200.avif 1200w"
     sizes="100vw"
     width="1200" height="675"            <!-- reserves space → no CLS -->
     alt="Team reviewing a dashboard on a laptop"
     fetchpriority="high"                     <!-- never loading="lazy" here -->
     decoding="async">

<!-- Every image below the fold -->
<img src="/img/card-400.webp" width="400" height="300" alt="…" loading="lazy" decoding="async">

Semantic skeleton

<body>
  <a class="skip-link" href="#main">Skip to content</a>
  <header>
    <a href="/" aria-label="Brand — home"><svg aria-hidden="true">…</svg></a>
    <button aria-expanded="false" aria-controls="menu">Menu</button>
    <nav id="menu" aria-label="Primary">…</nav>
  </header>
  <main id="main">
    <h1>One h1 per page</h1>
    <section aria-labelledby="features"><h2 id="features">…</h2></section>
  </main>
  <footer>…</footer>
</body>
  • Real <a href> for navigation, <button> for actions. Never a <div onclick>.
  • Every repeated card link carries context: Read more about X.
  • Forms: visible <label>, correct type and autocomplete attributes, errors linked with aria-describedby.
  • Keep the DOM shallow — avoid wrapper-in-wrapper markup that page builders generate.
  • Validate with the W3C validator; fix duplicate IDs immediately.

Phase 2 — CSS

CSS is render-blocking by design. The goal: the first paint needs only what is inline, and the rest never shifts the layout.

Split critical and non-critical CSS

Inline the styles for header, hero and the first viewport. Load the rest as one small, cacheable file. Generate critical CSS with a tool (e.g. critical, beasties) per template.

No @import, no CSS frameworks shipped whole

@import creates a serial request chain. If you use Tailwind or Bootstrap, purge unused classes at build time.

Reserve space for everything

aspect-ratio on media and embeds, fixed header height, min-height on slots that fill later (ads, reviews, consent bar).

Animate only transform and opacity

Animating top, left, width, height, margin triggers layout (CLS and “non-composited animation” warnings). Respect prefers-reduced-motion.

Use content-visibility for long pages

content-visibility: auto; contain-intrinsic-size: auto 600px; on below-the-fold sections skips their rendering work until needed.

Visible focus and accessible tokens

Never outline: none without a replacement. Define text/background pairs that already pass 4.5 : 1.

Font fallback that doesn’t shift fonts.css

@font-face {
  font-family: "Inter";
  src: url("/fonts/inter-var-latin.woff2") format("woff2");
  font-weight: 100 900;
  font-display: swap;             /* or optional for zero shift */
  unicode-range: U+0000-00FF, U+2013-2014, U+2018-201D, U+2026;
}
/* Metric-matched fallback: text keeps its size when Inter arrives */
@font-face {
  font-family: "Inter Fallback";
  src: local("Arial");
  size-adjust: 107%;
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}
body { font-family: "Inter", "Inter Fallback", system-ui, sans-serif; }

Override values differ per font — generate them with a tool such as Fontaine or Capsize rather than guessing.

Phase 3 — JavaScript

TBT is 30% of the score and INP is a Core Web Vital. JavaScript is the most expensive byte on the page: it has to download, parse, compile and execute on a slow CPU.

Do

  • Progressive enhancement: the page works and looks finished with JS off
  • Vanilla JS or tiny libraries; no jQuery on the front end
  • defer or type="module" on every script
  • Load features on interaction or visibility (IntersectionObserver, dynamic import())
  • Break long tasks with scheduler.yield()
  • Passive listeners for scroll / touch
  • Ship modern syntax only (no legacy polyfills for evergreen browsers)

Don’t

  • Render-blocking scripts in <head>
  • Carousels, parallax and scroll-animation libraries
  • Injecting above-the-fold content with JS
  • Reading layout then writing styles in loops (forced reflow)
  • Duplicate libraries (two versions of Swiper from two plugins)
  • unload event listeners
  • document.write

Third-party scripts: delay until they earn their place

// Load analytics / chat after the first user interaction, or after the page is idle.
const load3p = () => {
  if (window.__3pLoaded) return; window.__3pLoaded = true;
  const s = document.createElement('script');
  s.src = 'https://www.googletagmanager.com/gtag/js?id=G-XXXX';
  s.async = true;
  document.head.append(s);
};
['pointerdown', 'keydown', 'scroll'].forEach(e =>
  addEventListener(e, load3p, { once: true, passive: true }));
// Fallback so analytics still loads for passive readers
addEventListener('load', () => setTimeout(load3p, 5000));

Delaying analytics changes your data. Visitors who bounce instantly won’t be counted. That is an honest trade-off to discuss with the marketing team — not something to hide. Server-side tagging is the alternative that keeps both scores and data.

Facades for heavy embeds

Show a static thumbnail and a real <button> (“Play video: Product tour, 2 min”). Load the iframe only on click. This removes ~500 KB+ of JS, third-party cookies and several origins from page load. Same pattern for Google Maps (static image linking to Maps), chat widgets and social feeds.

Phase 4 — Images, fonts & media

Images are usually the LCP and the largest bytes on the page. Fonts are usually the cause of text-related CLS.

Lazy-loading rules

  • Never lazy-load the LCP image or anything in the first mobile viewport.
  • Lazy-load every other image and iframe with native loading="lazy" — no JS lazy-load libraries.
  • Use sizes that match the real layout ((min-width: 1024px) 33vw, 100vw) so phones download small files.

Phase 5 — Converting to WordPress

The conversion is where most hand-built 100s are lost. WordPress core, the block editor and plugins all add assets. Your job is to keep the output identical to your static build.

Conversion workflow

  1. Benchmark the static build firstRecord its Lighthouse scores per template. This is the baseline the theme must match.
  2. Build a custom theme — not a page builderA lean block theme (with theme.json) or a classic theme from your HTML. Page builders typically add 200–600 KB of CSS/JS and deep DOM nesting.
  3. Split HTML into templates and template partsheader.php/parts/header.html, front-page, single, archive, page, 404. Keep the exact markup.
  4. Enqueue assets the WordPress waywp_enqueue_style / wp_enqueue_script with defer strategy and file-time versioning, loaded only on templates that need them.
  5. Strip what core addsEmoji script, embeds, block-library CSS you don’t use, dashicons for visitors, jQuery.
  6. Use core image functionswp_get_attachment_image() outputs srcset, sizes, width/height and lazy-loading automatically.
  7. Compare against the baselineRe-run Lighthouse on each template. Any regression = something WordPress or a plugin added.

Asset loading & cleanup functions.php

<?php
// 1. Theme supports
add_action( 'after_setup_theme', function () {
  add_theme_support( 'title-tag' );                 // <title> per page (SEO + a11y)
  add_theme_support( 'html5', [ 'search-form', 'gallery', 'caption', 'style', 'script' ] );
  add_theme_support( 'responsive-embeds' );
} );

// 2. Enqueue only what you need, deferred, cache-busted by file time
add_action( 'wp_enqueue_scripts', function () {
  $css = 'assets/css/main.css';
  $js  = 'assets/js/main.js';
  wp_enqueue_style( 'theme', get_theme_file_uri( $css ), [], filemtime( get_theme_file_path( $css ) ) );
  wp_enqueue_script( 'theme', get_theme_file_uri( $js ), [], filemtime( get_theme_file_path( $js ) ),
    [ 'strategy' => 'defer', 'in_footer' => true ] );

  if ( is_page( 'contact' ) ) {                        // conditional assets per template
    wp_enqueue_script( 'contact', get_theme_file_uri( 'assets/js/contact.js' ), [], '1.0', [ 'strategy' => 'defer' ] );
  }

  if ( ! is_user_logged_in() ) wp_dequeue_style( 'dashicons' );
  wp_dequeue_style( 'classic-theme-styles' );
  // Only if you don't render core blocks on the front end:
  // wp_dequeue_style( 'wp-block-library' ); wp_dequeue_style( 'global-styles' );
}, 100 );

// 3. Remove head clutter and the emoji script
add_action( 'init', function () {
  remove_action( 'wp_head', 'print_emoji_detection_script', 7 );
  remove_action( 'wp_enqueue_scripts', 'wp_enqueue_emoji_styles' );
  remove_action( 'wp_head', 'wp_oembed_add_discovery_links' );
  remove_action( 'wp_head', 'rsd_link' );
  remove_action( 'wp_head', 'wlwmanifest_link' );
  remove_action( 'wp_head', 'wp_generator' );
  remove_action( 'wp_head', 'wp_shortlink_wp_head' );
  add_filter( 'emoji_svg_url', '__return_false' );
} );

// 4. Drop jQuery Migrate on the front end (only if no plugin needs it)
add_action( 'wp_default_scripts', function ( $scripts ) {
  if ( ! is_admin() && isset( $scripts->registered['jquery'] ) ) {
    $scripts->registered['jquery']->deps = array_diff( $scripts->registered['jquery']->deps, [ 'jquery-migrate' ] );
  }
} );

What WordPress does for you — and when it gets it wrong

Automatic lazy-loading and fetchpriority

Core skips lazy-loading the first content images and adds fetchpriority="high" to the likely LCP image. It guesses from content order — verify it chose your actual hero, especially when the hero comes from a custom field or a block pattern.

WebP and AVIF uploads

Core accepts both (AVIF where the server’s image library supports it). Convert on upload with a tool or plugin; keep originals out of the front end.

Speculative loading

Recent WordPress versions output Speculation Rules that prefetch links on hover-intent. This speeds up real navigations (field LCP) without affecting the lab score. Keep it on.

Block library CSS and global styles

Block themes inline per-block CSS and global styles. Usually fine (only used blocks load), but large theme.json palettes and presets bloat the inline <style>. Trim unused presets.

Plugin discipline

Plugin rules

  • Audit every plugin’s front-end output (Query Monitor, DevTools Coverage)
  • One caching / optimisation plugin, configured — or none if the host caches
  • Forms and sliders load assets only on pages that use them (use the asset-unloading feature or a code snippet)
  • SEO plugin outputs title, description, canonical — remove duplicates from the theme
  • Accessible cookie banner, fixed-position, no layout shift

Usual offenders

  • Page builders and “mega add-on” packs
  • Slider / carousel plugins
  • Social share and Instagram feed widgets
  • Font Awesome and Google Fonts loaded by plugins
  • Popup builders that load on every page
  • “All-in-one” optimisation plugins that inline everything (can increase HTML size and break CSP)

Phase 6 — Hosting & server

You can’t optimise your way past a slow server. Uncached WordPress takes 300–1,500 ms to generate a page; cached HTML from a CDN edge takes 20–80 ms.

Full-page cache

Server-level (Nginx FastCGI cache, LiteSpeed Cache, Varnish) or a host that provides it. Logged-out HTML must never hit PHP.

TTFB

CDN with HTML caching

Cache the HTML at the edge, not just static files, so PSI’s test location gets a nearby response.

TTFB

Modern stack

A current, supported PHP 8.x release with OPcache; persistent object cache (Redis/Memcached) for dynamic and logged-in pages; HTTP/2 or HTTP/3; TLS 1.3.

TTFB

Compression

Brotli (or gzip) for HTML, CSS, JS, SVG, JSON. Never compress already-compressed images and fonts.

FCP

Long-lived caching for versioned assets

One year + immutable for CSS/JS/fonts/images with version strings. Flagged by the “Use efficient cache lifetimes” insight.

Repeat views

No redirect chains

Pick one canonical host (https + www or not) and redirect in one hop. The tested URL should return 200 directly.

FCP

Caching & security headers .htaccess (Apache / LiteSpeed)

# Long cache for versioned static assets
<IfModule mod_headers.c>
  <FilesMatch "\.(css|js|woff2|avif|webp|jpe?g|png|svg|ico)$">
    Header set Cache-Control "public, max-age=31536000, immutable"
  </FilesMatch>

  # Security headers (Trust & Safety audits)
  Header always set Strict-Transport-Security "max-age=63072000; includeSubDomains; preload"
  Header always set X-Content-Type-Options "nosniff"
  Header always set Referrer-Policy "strict-origin-when-cross-origin"
  Header always set Cross-Origin-Opener-Policy "same-origin"
  Header always set Content-Security-Policy "frame-ancestors 'self'"
  Header always set Permissions-Policy "geolocation=(), camera=(), microphone=()"
</IfModule>

# Brotli, falling back to gzip
<IfModule mod_brotli.c>
  AddOutputFilterByType BROTLI_COMPRESS text/html text/css application/javascript image/svg+xml application/json
</IfModule>
<IfModule mod_deflate.c>
  AddOutputFilterByType DEFLATE text/html text/css application/javascript image/svg+xml application/json
</IfModule>

Start HSTS with a short max-age and only add preload once every subdomain serves HTTPS. On Nginx, set the equivalent add_header / expires directives.
